Have you used the MAST multi-mission search forms? 
Have you wondered how we organize that and provide data from across all missions in a single table for you?
Are you perhaps wondering if you should use a multi-mission search vs a single-mission search form?
If so, read on to learn more about how we handle information from multiple missions at MAST!

One of the greatest challenges when working with different sorts of data is taking various pieces of information and ensuring they have the same meaning and the same types of values. Take something as simple as the name of an astronomy filter. Some missions may store it as a FITS header keyword called FILTER, others may use FILTERNAME, others may store it in an ASDF header under meta.optical_element. Similarly, consider something like the values of exposure time. Is it in seconds? Hours? Minutes? Even if every mission called it EXPOSURE, we may have mismatches with the units being stored in that field. As you can imagine, these sorts of issues can crop up for any column or field in the metadata. Essentially every mission will have its own preferred way of organizing this. This is where a common model comes to the rescue.

Introducing the Common Archive Observation Model. This model, also known as CAOM, is the answer to our woes with each mission having different ways of representing metadata. It was designed in collaboration with the Canadian Astronomical Data Centre (CADC), used across several astronomical archives, and is proposed as an astronomical standard in the International Virtual Observatory Alliance (IVOA). We at MAST use CAOM to store metadata across all missions in a consistent framework that facilitates easier searching.

## What is CAOM?

CAOM is a hierarchical data model that stores metadata for observations and files in a consistent manner. At its top layer is the "Observation", which represents the global properties of a dataset, such as proposal information, the intended target, the telescope used, the instrument, and things of that nature. 
For each Observation there can be one or more "Planes". A Plane represents the physical properties that pin the data to some location in the sky, at some time, with some astronomical filter. This is where we define the footprints of an observation and while that naturally includes coordinates in degrees, we also store wavelength range in meters, and the start and end times of our data in days. This is also where we store how processed a dataset is—the calibration level.
For each Plane, there can be one or more "Artifacts". An Artifact represents a file or product available for retrieval. We store book-keeping information like checksums and sizes here, in addition to the actual filenames and retrieval information.
There are a few more advanced concepts, but this is the gist of the model. With this, we can describe the properties of a dataset encapsulated into an Observation with its Planes and Artifacts.

## What do we get by using CAOM?

The most obvious result is that we have a consistent set of columns that represent the same information across all missions. In CAOM, the telescope name is under Observation.telescope.name. When we convert metadata into this model, we make sure to populate it there so that our search interface will always find it in the same place each time. It doesn't matter if you are searching HST or Roman or High-Level Science Products (HLSPs). When you get a table of CAOM results you'll see the same information in shared columns for easy comparisons and searching.

## Why not use CAOM all the time?

The biggest issue with CAOM is the loss of specificity. If there is a telescope that had 3 filter columns, CAOM may combine them into a single value, but if you wanted to search all three with different bits of information, you're out of luck. Also, while CAOM can store arbitrary keywords, they aren't designed for searching, so if you have a very specific field you wanted to extract you also may not be able to find it. And because CAOM forces all missions into its own standard, it loses mission-specific meaning. For example, in Roman a level 5 product represents community-contributed products, which are stored as level 4 in CAOM (and other missions).

## How do you pick which one to use?

Well, if you want a quick look at MAST holdings, or to see observations across multiple missions, pick our MultiMission option with CAOM. If you want a detailed look at a specific mission, perhaps to search for explicit keywords in file headers, pick the Single Mission option. 
If you navigate the MAST Portal at https://mast.stsci.edu you are, by default, looking at the CAOM multi-mission database. 
If you instead navigate to the more modern MAST Search interface at https://mast.stsci.edu/search/ui/#/ you get to choose which mission you want to search with a single-mission search (in the future, we will have CAOM in the new form as a "Cross-Mission Search" option).
If you use Astroquery, the `astroquery.mast.Observations` class utilizes CAOM on the backend, while mission-specific queries are handled via `astroquery.mast.MastMissions`.

We hope this has been an instructive guide into these two approaches to searching data. In the end, the files themselves are the same. By providing these two approaches we can tailor the experience for discovering data across the full spectrum of what MAST has to offer, while also empowering users that are more savvy about mission-specific details.
